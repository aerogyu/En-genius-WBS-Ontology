# WBS 도구 정식 개발 — 요구사항 (초안, 2026-11-12)

Leo 와의 논의(2026-11-12)를 정리한 것. 아키텍처 설계(데이터 모델·화면·API·이관)는 이 문서가 확정된 뒤 따로 한다 (Fable 권장).

## 1. 왜 정식 개발인가

- **MS Project 를 쓸 수 없다** — 연구소 전체 라이선스 5개. 정본은 이미 엑셀이고, 앞으로 WBS 작성·수정은 이 도구에서 한다.
- **진짜 일은 취합 뒤 전체 수정** — 모듈마다 작성한 것을 합친 뒤 전체를 보며 고칠 곳이 많다. 지금 v0.4(한 장 HTML + apply)는 혼자 쓰는 '가정 편집' 도구라 감당 못 한다.

## 2. 사용자·권한

| 역할 | 인원 | 할 수 있는 것 |
|---|---|---|
| 관리자 | 3~4 (Leo 포함) | 전체 편집 · 취합·판 확정 · 수정 요청 처리 · 권한 관리 |
| 모듈 리더 | 모듈 수만큼 | **자기 모듈만** 편집 · 다른 모듈에 **수정 요청**(예: "내 업무의 선행이 될 업무가 없음 — 만들어 달라") |
| 조회자 | 나머지 (전체 20~30명) | 보기·검색·내려받기만 |

## 3. 작성 흐름 — 지금과 제안

**지금 (엑셀 왕복)**: 모듈별 업무 작성 → 취합 → 재배포 → 각자 선행 업무를 찾아 기입 → 다시 취합 → 1차본. 이후 수정도 '취합 → 모듈 수정 → 재취합' 반복.
왕복마다 번호(A열)가 바뀌어 모듈 간 선행이 깨지기 쉽고, 누가 무엇을 바꿨는지 남지 않는다.

**제안 (서버 한 곳에 정본)**: 상시 켜 둔 PC 에 도구를 띄우고 모두 사내망 브라우저로 접속 (En-genius 서버 테스트와 같은 방식 — 가능 확인됨).
- 1차본 엑셀을 한 번 들여와 업무마다 **고유 ID** 를 붙인다 (번호·WBS 코드가 바뀌어도 그대로).
- 모듈 리더는 **자기 모듈을 브라우저에서 바로 고친다** — 취합 단계가 사라진다. 선행은 번호를 외워 적지 않고 **다른 모듈 업무를 검색해서 고른다**.
- 걸 선행이 없으면 그 모듈에 **수정 요청**을 남긴다 → 그 모듈 리더(또는 관리자)가 처리.
- 관리자는 언제나 전체를 본다 — 검사(C코드)·주경로·월별 공수가 실시간.
- 모아 둘 시점에 **판 확정**(1차본·2차본 …, 그대로 얼려 둠) — 판끼리 비교.
- **엑셀 왕복은 계속 지원**: 전체·모듈별 엑셀 내보내기(지금 양식 그대로), 엑셀로 고쳐 온 것 들여오기(바뀐 점을 보여 주고 확인 뒤 반영). 서버에 못 들어오는 경우·대량 작성용.

## 4. 기능 — 단계별 (필요해지면 그때 추가)

**1단계 (최소 — 지금 흐름을 서버로)**
- 1차본 엑셀 들여오기 · 고유 ID · 로그인 · 모듈별 권한
- 표 + 간트에서 편집: 업무 추가·삭제·이동, WBS 코드 다시 매기기, 기간·날짜·선행(검색해서 고름)·이름·MH·산출물
- 날짜 다시 짜기·주경로·검사·월별 공수 (v0.2~v0.4 엔진 그대로)
- 변경 이력 (언제·무엇을·누가 — 6장 B) · 수정 요청 목록
- 판 확정 · 엑셀 내보내기(전체·모듈별) · 보고서·TTL

**2단계**: 판 비교(기준 일정 대비 밀린 것) · 휴일 달력 · 엑셀로 고쳐 온 것 들여오기 · 알림(요청이 왔음)
**3단계**: 실적·진척률 · 인력 평준화(아래) · 다른 온톨로지(Tool·워크플로·자료 조사)·MCP 연계

**인력 평준화란**: 같은 팀(자원)이 한 시기에 감당 못 할 만큼 업무가 겹치면, 여유가 있는 업무를 그 여유 안에서 뒤로 미뤄 겹침을 푸는 기능. 쓰려면 업무마다 '어느 자원이 맡나'와 자원마다 '가용 인원'이 있어야 한다 — 지금 WBS 에는 투입인력 숫자만 있다. 그 전 단계로 월별 공수(이미 있음)를 팀별로 나눠 과부하를 **보는** 것부터. 자원은 사람이 아니라 팀·역할 단위로 둔다 (인명 저장 금지).

## 5. 기술 원칙

- 폐쇄망·반입 최소·허용형 라이선스 (Tool 온톨로지와 같은 규칙).
- 정본 = 도구의 데이터베이스(표준 라이브러리 SQLite). 엑셀은 들여오기·내보내기 형식.
- 웹 서버: 표준 라이브러리만으로도 되지만 여러 사람·로그인·세션을 직접 짜는 것은 위험 부담이 크다. **Tool 온톨로지 MCP 묶음으로 이미 반입된 `starlette`·`uvicorn`(BSD)** 을 쓰면 새 반입 없이 갈 수 있다 — 설계 때 결정.
- 지금 엔진(parse·analyze·schedule·apply·report·rdfout)은 그대로 바닥으로 쓴다. 보기 HTML 의 화면 코드도 대부분 옮겨 쓴다.
- 같은 저장소(`engenius-wbs-ontology`)에서 키운다.

## 6. Leo 확인 질문

- **A. 정본을 엑셀에서 도구 데이터베이스로 옮기는 것** — 이후 엑셀은 '내보낸 사본'이 된다. 괜찮은가?
- **B. 변경 이력의 '누가'** — 저장소 규칙상 인명은 저장하지 않는다. ① 개인 계정(사번 등 — 규칙 예외로 둠) ② 모듈 계정('FAN 리더' 처럼 역할 단위, 사람 이름 없음). 권장 ②로 시작.
- **C. 로그인** — 사내 계정(SSO) 연동이 되나, 아니면 도구 자체 계정(관리자가 발급)인가.
- **D. 서버 PC 에 사업 WBS 를 두고 사내 공유** — 보안 정책상 괜찮은가 (En-genius 서버 사례와 같은 취급인가).
- **E. 모듈 = Lv1 구성품** 인가? 모듈 리더는 몇 명? 공통 모듈(체계종합·사업관리 등)의 편집 권한은 누구에게?
